# 입실 구분 기획서: 예약 · 키오스크 워크인 · 프론트

- 작성일: 2026-11-11
- 대상: 객실 리모컨 웹앱 (`index.html`), 이글(iCrew Eagle) API
- 상태: 1차 개발 완료 (2026-11-11). 디자인은 다시 다듬을 예정

## 1. 목적

입실 한 건 한 건을 **예약 / 키오스크 워크인 / 프론트** 세 가지로 나눠서 월별·일별로 셀 수 있게 한다.
지금은 워크인(예약 없이 와서 결제하는 손님)이 몇 건인지 따로 볼 방법이 없다. 이글 API의 입실 기록만으로 자동으로 나눈다.

## 2. 구분 기준

입실 기록(`room-sale`)의 두 값만으로 판단한다. 모든 입실이 셋 중 정확히 하나에 들어간다.

| 구분 | 판단 기준 | 설명 |
|---|---|---|
| **예약** | `room_reserve_id` 있음 | OTA·네이버 등 예약과 연결된 입실. 입실 경로(키오스크·프론트)와 관계없이 예약으로 본다. |
| **키오스크 워크인** | `room_reserve_id` 없음 + `channel_type = KIOSK` | 예약 없이 키오스크에서 바로 결제하고 들어온 손님. |
| **프론트** | `room_reserve_id` 없음 + `channel_type`이 `FRONT`·`USER`·`APP`·`DEVICE`·`API` | 직원이 이글 PC, 이 웹앱, 관리자 계정으로 직접 입실 처리한 건. |

판단 순서: ① 예약 번호가 있으면 **예약**으로 확정한다. ② 없으면 입실 주체가 키오스크인지 보고 **키오스크 워크인**과 **프론트**로 나눈다.

### 왜 결제 수단으로 나누지 않는가

- 예약인데 현장에서 카드로 결제하는 건이 있다 (11월에 2건). 카드 결제만 기준으로 잡으면 이 건이 워크인으로 잘못 세어진다.
- 프론트에서 입실시킨 건은 이글에 결제 기록이 없는 경우가 많다. 결제 수단을 기준으로 잡으면 이 건이 빠진다.
- 그래서 결제 수단(`payments[].type`)은 **구분 기준이 아니라 참고 정보**로만 보여 준다.

## 3. 사용하는 API 값

| 필드 | 값 | 뜻 |
|---|---|---|
| `room_reserve_id` | 문자열 / 비어 있음 | 예약 입실이면 예약 ID |
| `channel_type` | `KIOSK`, `FRONT`, `USER`, `APP`, `DEVICE`, `API` | 입실 주체 |
| `stay_type` | `HOURS`(대실), `DAYS`(숙박), `LONG_DAYS`(장기), `OTHER` | 입실 유형 (보조 분류) |
| `payments[].type` | `CARD`, `CASH`, `AGENT`(OTA 선결제), `ACCOUNT`, `MILEAGE`, `NOT_PAID` | 결제 수단 (참고) |
| `payments[].amount_paid_creadit_card`, `accepted_cash`, `changed_cash` | 숫자 | 현장 결제 금액 계산용 (철자는 API 그대로) |

조회 엔드포인트:

- 기간별 입실 기록: `GET /v1/room-sale/all/{accom_id}?year=YYYY&month=M[&day=D]`
- 현재 입실 중: `GET /v1/room-sale/all-activated/{accom_id}` (이미 웹앱이 쓰는 요청)

## 4. 실데이터 검증 (2026년 11월 1~11일, 52건)

| 구분 | 건수 | 세부 |
|---|---|---|
| 예약 | 35건 | 키오스크 26건 (OTA 선결제) · 키오스크 2건 (현장 카드) · 키오스크 1건 (미결제) · 프론트 6건 (OTA 선결제) |
| 키오스크 워크인 | 8건 | 전부 키오스크 카드 결제, 숙박 |
| 프론트 | 9건 | 프론트 8건 · 관리자 계정 1건, 모두 이글에 결제 기록 없음 |

세 구분의 합이 52건으로 전체와 같아 빠지거나 겹치는 건이 없다.

## 5. 화면 기획

### 5-1. 월별 집계 (새 화면)

- 위치: 하단 탭바 오른쪽 끝에 **[집계]** 탭을 추가한다. 첫 화면은 지금처럼 객실 현황을 유지한다.
- 상단: 월 선택 (‹ 2026년 11월 ›)
- 요약 카드 3개: **예약 35 · 키오스크 워크인 8 · 프론트 9** (건수 + 전체 대비 비율)
- 키오스크 워크인 카드에만 **현장 결제 합계 금액**을 함께 보여 준다.
- 아래 목록: 일자별 행 (날짜 · 예약 · 워크인 · 프론트). 행을 누르면 그날의 입실 목록(객실, 시간, 대실/숙박, 결제 수단)을 펼친다.
- 대실·숙박 필터 칩: 전체 / 대실 / 숙박

### 5-2. 객실 카드·입실 시트 표시

- 사용중 객실 카드의 손님 이름 옆에 작은 배지를 붙인다: `예약` / `워크인` / `프론트`.
- 객실을 누르면 나오는 시트의 정보 목록에 "입실 구분" 줄을 추가한다.
- 이미 불러오는 현재 입실 기록에 필요한 값이 있으므로 추가 요청은 없다.

## 6. 조회 규칙 (이글 API 차단 방지)

이 웹앱의 기존 원칙을 그대로 따른다.

- 자동 반복 조회(폴링)·정기 일괄 조회를 하지 않는다.
  - 예외(2026-11-12 사용자 허락): 인사이트(dimansion-insight)가 하루 2번(11:00·15:30) 이번 달 입실 기록을 한 번씩 받아 저장한다. 이 웹앱의 원칙은 그대로다.
- 집계 탭은 **탭을 열 때와 월을 바꿀 때만** 해당 월 기록을 한 번 조회한다.
- 지난달 이전 기록은 바뀌지 않으므로 앱 안에 저장해 두고 다시 조회하지 않는다. 이번 달은 최소 15초 간격을 둔다.
- 일자별 상세는 월 조회 결과에서 나눠 보여 주고, 날짜별로 따로 요청하지 않는다.

## 7. 한계와 운영 보완

- **프론트 건의 금액은 API로 알 수 없다.** 직원이 결제를 따로 받고 입실만 처리하기 때문이다. 금액이 필요하면 운영시트 값을 쓴다.
- 프론트 건에는 전화 예약, 무료 제공, 현장 결제가 섞여 있을 수 있다. 앞으로 더 나누려면 프론트 입실 때 이 웹앱의 입실 시트에서 결제 수단(카드·현금)을 함께 입력하도록 운영한다. 그러면 `payments`에 기록이 남아 집계에 잡힌다.
- 예약이 이글에 늦게 들어와 예약 연결 없이 입실 처리된 건은 프론트로 잡힌다. 예약은 입실 전에 배정 탭에서 연결해 두는 것을 원칙으로 한다.
